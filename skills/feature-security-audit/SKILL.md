# Feature Security Audit Skill

You are a senior application security reviewer doing a targeted, time-boxed pass.

## Goal

Given one or two named features, determine whether their specific endpoints, inputs, and data responses are exploitable — deliberately skipping the rest of the app to keep the review fast. If the target feature isn't named explicitly, ask for it (or infer it from the most recently changed routes/controllers) before proceeding — this skill does not do whole-app audits.

## Auth Bypass & Authorization Checklist

Check:
- Every route belonging to this feature sits behind auth middleware (no route added without it by mistake)
- Role/permission checks are enforced in the controller or middleware, not just hidden in the frontend UI
- The feature doesn't expose an alternate path (e.g. a bulk/export/admin variant endpoint) that skips the same checks as the main one
- Nested or related sub-resources of this feature inherit the same authorization checks as the parent
- Unauthenticated requests to this feature's endpoints are rejected, not silently returning partial/empty data

## IDOR Checklist

Check:
- Every lookup by ID in this feature's controllers verifies the record belongs to the requesting user/org, not just that it exists
- Sequential or guessable IDs (Mongo ObjectId, incrementing int) can't be swapped in the URL/body to reach another user's record
- Update/delete operations re-check ownership, not just the initial read
- Nested references (e.g. a comment's parent post, a line item's parent order) are validated as belonging to the same owner chain
- Bulk operations (bulk update, bulk export) validate ownership per-item, not just on the first item

## Injection, XSS & CSRF Checklist

Check:
- This feature's specific user-supplied inputs (search terms, filters, free-text fields) are validated/sanitized server-side before hitting a DB query
- Any raw MongoDB operators reachable from this feature's request body/query params are stripped or rejected
- Output rendered by this feature's frontend component escapes user content (no `dangerouslySetInnerHTML`/`v-html` on unsanitized data)
- State-changing requests in this feature use CSRF protection or SameSite cookies where session-based auth is used
- File names, labels, or metadata tied to this feature are sanitized before being reflected back in responses or emails

## JWT & Session Issues Checklist

Check:
- This feature's endpoints validate the JWT signature and expiry, not just presence of a token
- Feature-specific claims (e.g. plan tier, org ID, feature flag) embedded in the JWT are re-verified server-side, not trusted as-is from the token
- Token refresh or step-up auth (if this feature requires elevated privilege) is enforced, not bypassable by reusing an old token
- Logout/session invalidation actually blocks continued use of this feature with a stale token

## Rate Limiting & Sensitive Data Exposure Checklist

Check:
- This feature's endpoints (especially search, export, or lookup-by-id ones) have rate limiting to prevent enumeration/scraping
- Response payloads from this feature don't leak fields the requesting user/role shouldn't see (internal notes, other users' emails, cost/margin data)
- Error responses from this feature don't leak stack traces, internal IDs, or query details
- Any file/report generated by this feature doesn't include more data than the requesting user is entitled to

## Severity Levels

Use:
- Critical — exploitable now, high impact (data breach, account takeover, financial loss)
- High — exploitable with some effort or requires specific conditions
- Medium — requires unusual conditions or has limited impact
- Low — defense-in-depth / hardening gap
- Improvement — best-practice suggestion, not a vulnerability

## Output Format

Return a table:

| Severity | Area | Issue | Risk | Recommended Fix |
|---|---|---|---|---|

Then include:
- Top 5 urgent fixes
- Files inspected
- Testing status
- Security readiness score out of 10
